**Video upscale — the blocking assumption was measured and it was wrong (2026-09-03).** The recon
note said an ESRGAN pass is output-pixel-driven, stacks on resident weights, and "will not fit
alongside LTX's ~31 GB". Measured on the live core, a batch of frames through
`UpscaleModelLoader → ImageUpscaleWithModel` at 4×:

| source | frames | output | peak VRAM | marginal | time |
|---|---|---|---|---|---|
| 832×480 | 1 | 6.4 MP | — | ~0 | 2.9 s |
| 832×480 | 8 | 6.4 MP | 2.46 GB | +0.68 | 6.6 s |
| 832×480 | 25 | 6.4 MP | 4.70 GB | +2.92 | 19.8 s |
| 832×480 | 49 | 6.4 MP | 4.81 GB | **+3.03** | 38.1 s |
| 832×480 | **97** | 6.4 MP | 5.02 GB | **+3.25** | 75.5 s |
| 1024×640 | 49 | 10.5 MP | 5.14 GB | **+3.36** | 66.8 s |

**The marginal cost is bounded and essentially frame-count independent** — 49 frames and 97 frames
both cost about 3.3 GB, because the node streams frames rather than holding the batch. What scales
with frame count is **time**: ~0.78 s/frame at 6.4 MP output, ~1.36 s/frame at 10.5 MP. A 97-frame
render would gain about 75 s.

So video upscale is not blocked by VRAM in the way the note claimed. Measurement script:
`build/video_upscale_cost.json`.

#### ✅ SHIPPED + RENDER-PROVEN 2026-09-03 — and the residency question answers itself

The one thing the table above could not answer was **residency at the moment it runs**: the pass
happens after decode, and whether the transformer is still resident then decides whether +3.3 GB
fits under the ceiling. Measured on the live core through the **shipping builder**, LTX two-stage
768×512×49f, **seeds varied between the two runs** so neither was served a cached latent:

| | peak VRAM | wall clock | output |
|---|---|---|---|
| baseline, no upscale | **31.55 GB** | 79.3 s | 1536×1024×49f |
| with the model upscale | **31.70 GB** | 285.4 s | **3072×2048×49f** |

**+0.15 GB, not +3.0.** The two numbers do not stack: peak is set by the SAMPLER, and ComfyUI has
already freed the transformer by the time a node one hop after VAE decode runs. The isolated +3.0 GB
was measured against an idle card, where there was no larger peak for it to fit under. **What a
video upscale costs on a real render is time, not headroom** — 79 s → 285 s for 49 frames.

Three defects were found on the way, all of the same shape as the one that started this section —
*the answer was wrong and looked ordinary*:

1. **`graft_pixel_upscale` searched for the literal `"SaveImage"`.** Every native video family ends
   `…VAEDecode → CreateVideo(images) → SaveVideo`, so the search found nothing and the graft
   returned the graph untouched. No upscale, no complaint. `IMAGE_SINKS` is now the table both
   grafts search, and `tests/test_upscale_reaches_every_family.py` holds the builders to it.
2. **The route resolver only knew image families**, so `ltx`/`wan`/`hunyuan`/`mochi` resolved to
   `pixel_pil` — the diffusers post-pass, which never sees a picture ComfyUI produced. Nobody
   performed it. The video list is now read from `NATIVE_VIDEO_FAMILY_PLUGINS`, not restated.
3. **The frame is not the request.** On the default LTX route `LTXVLatentUpsampler` runs between the
   two samplers, so `req["width"]` is the size of the **latent**: a request for 768×512 renders a
   1536×1024 file. The first version of the graft targeted `req["width"] × scale` = 1536, which the
   frame already was — a 4× model upscale followed by a resize straight back to the size it started
   at. Bigger file, identical dimensions. The target is now derived from the graph.

**OPEN, named here rather than fixed quietly — the size you set is not the size you get.** On the
default LTX route the cockpit's 768×512 delivers 1536×1024. Nothing *claims* the wrong number (the
native video runner records no dimensions in its completion payload), so this is not a lie in the
result — but it is a control that does not describe its output, and Simple mode's whole promise is
intent-level controls that mean what they say. Fix belongs with the Simple-mode size story, beside
"target resolution as a tier", which needs the same second axis.
